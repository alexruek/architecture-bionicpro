# Решения по заданию 1. Повышение безопасности системы

Значения параметров (время жизни токенов и сессий, адреса, имена) заданы в `config/defaults.toml`, здесь они не повторяются.

## Противоречия и опечатки в задании

1. Задача 2 предлагает разобраться с PKCE по разделу документации Keycloak о Device Authorization Grant. Это другой grant. PKCE реализован по RFC 7636: у клиента Keycloak задан атрибут `pkce.code.challenge.method`, без `code_challenge` Keycloak отклоняет запрос авторизации.
2. Задача 2 требует добавить PKCE к фронтенду, а задача 3 переносит получение токенов из фронтенда в бэкенд. PKCE выполняет bionicpro-auth: он создает `code_verifier`, передает `code_challenge` в запросе авторизации и `code_verifier` при обмене кода. Фронтенд только начинает вход переходом на `/auth/login`. Публичный клиент `reports-frontend` удален из realm, чтобы токены нельзя было получить в браузере.
3. Пункт 12 задачи 3 требует вернуть новый session id в ответе фронтенду. Новый id передается в заголовке `Set-Cookie` того же ответа и в тело не попадает: если отдать id скрипту, флаг HttpOnly теряет смысл.
4. В `ldap/config.ldif` из репозитория спринта запись имела DN `uid=alex`, атрибут `uid: alex.johnson`, а группа `prothetic_user` ссылалась на несуществующий DN `uid=alex.johnson`. Пользователь не получал роль. DN исправлен на `uid=alex.johnson`, согласованность ldif проверяет `tests/test_ldap_ldif.py`.
5. Задача 6 требует запрашивать профиль у Яндекса и сохранять его в БД. Профиль запрашивает Keycloak у `login.yandex.ru/info` при каждом входе, пользователь и атрибуты профиля (маппинги `yandex_*`) сохраняются в БД Keycloak (PostgreSQL).

## Архитектура управления учетными данными

Диаграмма: `diagrams/bionicpro-c4-security.drawio`.

1. Единая точка входа - Keycloak в контуре России. Он работает как брокер: локальные учетные записи, каталог представительства по LDAP и внешние IdP (Яндекс ID, в перспективе национальные IdP по OIDC или SAML 2.0) подключаются к одному realm. Приложения знают только Keycloak и bionicpro-auth, набор IdP меняется без изменения приложений. Выбор IdP передается параметром `kc_idp_hint`.
2. Каталог представительства подключен через User Federation в режиме `READ_ONLY` без импорта. ФИО, email и группы читаются из LDAP в момент входа и не копируются в БД Keycloak, поэтому персональные данные остаются в стране представительства. В БД Keycloak остаются только ссылка на федеративного пользователя, OTP-секрет и согласия. Группы LDAP отображаются на роли realm маппером `role-ldap-mapper`, так роли разных представительств сводятся к единой ролевой модели. В промышленной среде соединение идет по LDAPS через защищенный канал между странами, стенд использует `ldap://` образа osixia.
3. Токены не покидают сервер. bionicpro-auth выполняет authorization code flow с PKCE как конфиденциальный клиент, проверяет подпись, issuer, audience и nonce в `id_token`, хранит токены в Redis и выдает браузеру только cookie сессии с флагами HttpOnly и Secure.
4. Хранение токенов. Redis выбран как распределенный кеш, чтобы bionicpro-auth можно было масштабировать горизонтально. access_token и refresh_token шифруются (Fernet: AES-128-CBC и HMAC-SHA256) ключом `TOKEN_ENCRYPTION_KEY`. Без ключа сервис создает его в памяти, после перезапуска нужен повторный вход. В Redis ключом записи служит SHA-256 от session id, сам id не хранится.
5. Время жизни. Сессия живет дольше access_token и не дольше refresh_token (SSO Session Idle). Когда до истечения access_token остается меньше запаса `ACCESS_TOKEN_REFRESH_MARGIN_SECONDS`, bionicpro-auth сам обновляет его через refresh_token. Если Keycloak отклонил refresh_token, сессия удаляется и пользователь входит заново.
6. Ротация сессии. Каждый запрос к `/auth/session` и `/api/*` переносит токены на новый session id атомарно (WATCH/MULTI в Redis) и обновляет cookie. Старый id на короткое окно grace становится ссылкой на новый, чтобы параллельные запросы страницы не обрывали сессию. После окна старый id недействителен.
7. Защита от CSRF. Cookie с SameSite=Lax, для изменяющих запросов проверяется заголовок Origin. Параметр `state` привязан к браузеру отдельной HttpOnly cookie, `nonce` защищает от подмены `id_token`.
8. Фронтенд и bionicpro-auth работают на одном origin: nginx фронтенда проксирует `/auth/` и `/api/`. CORS не нужен, cookie не уходит на сторонние домены.
9. MFA. Поток `browser-mfa` - копия стандартного browser flow, где OTP Form обязателен, а не условен. Пользователь без настроенного OTP при первом входе получает обязательную настройку Google Authenticator или FreeOTP. Для входа через внешние IdP OTP требует поток `post-broker-otp`. Включена защита от перебора.
10. Согласие. У клиента bionicpro-auth включен `consentRequired`: после аутентификации, в том числе через Яндекс ID, Keycloak спрашивает разрешение на передачу профиля. Яндекс дополнительно показывает свой экран доступа. При `consentRequired` Keycloak по умолчанию выключает full scope, поэтому `fullScopeAllowed` задан явно, иначе роли не попадают в токен.
11. Яндекс ID. В Keycloak 21 нет встроенного провайдера Яндекса, а стандартный OIDC-провайдер требует `id_token`, которого OAuth Яндекса не выдает. Используется провайдер `yandex` из библиотеки playa-ru/keycloak-russian-providers, собранной под Keycloak 21. Образ Keycloak собирается из `keycloak/Dockerfile`. Client ID и секрет приложения Яндекса подставляются в realm при импорте из переменных окружения и в репозиторий не попадают.
12. `revokeRefreshToken` выключен: при одноразовых refresh_token два параллельных обновления одной сессии приводили бы к ее потере. Компенсирующие меры: refresh_token хранится только на сервере в зашифрованном виде и не передается клиенту.
13. Keycloak выдает токены с публичным issuer (`KC_HOSTNAME_URL`), а bionicpro-auth обращается к нему по внутреннему адресу, для этого включен `KC_HOSTNAME_STRICT_BACKCHANNEL=false`.
14. Секрет клиента bionicpro-auth для локального стенда записан в realm и docker-compose, как секрет `reports-api` в исходном realm. В промышленной среде секреты передаются через хранилище секретов.
15. Экспорт `keycloak/keycloak-results-export.json` делается частичным экспортом realm: секреты в нем замаскированы, пользователи и их OTP-секреты не выгружаются.
